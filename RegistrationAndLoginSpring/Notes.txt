Lessons learned while working on this spring project 


Lesson 1
1.You should not put a class annotated with @SpringBootApplication in the default package (which is java create a nested package) because @SpringBootApplication enables component scanning, and without a named package Spring doesn't have a proper package boundary for that scan.

	The key idea
		Suppose you have:
		@SpringBootApplication
		public class MyApplication {
		    public static void main(String[] args) {
		        SpringApplication.run(MyApplication.class, args);
		    }
		}
		and there is no:
		package com.example.myapp;

		Then MyApplication is in the default package.

		@SpringBootApplication includes @ComponentScan.

		Conceptually:

		@SpringBootApplication
		        │
		        ├── @Configuration
		        ├── @EnableAutoConfiguration
		        └── @ComponentScan
		                ↓
		        Find Spring components

		Normally, Spring uses the package containing your application class as the starting point.

		For example:

		com.mycompany.registration
		        │
		        ├── RegistrationApplication
		        ├── controller
		        ├── service
		        └── repository

		Spring can effectively scan:

		com.mycompany.registration

		and its subpackages.

		But with the default package:

		(default package)
		        │
		        └── MyApplication

		there is no meaningful package namespace to use as the scan boundary.

		Spring may therefore end up scanning classes across the classpath/JARs, including framework classes and configuration classes that it should not be scanning as your application's components.

		That's why Spring Boot warns:

		Your ApplicationContext is unlikely to start due to a
		@ComponentScan of the default package.

-------------------------------------------------------------------------------------------------
package com.example.auth;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class Application {

    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

import ...SpringApplication — Boot's bootstrap class.
import ...SpringBootApplication — the meta-annotation.
@SpringBootApplication — combines three annotations:
	@SpringBootConfiguration (a specialization of @Configuration — marks the class as a source of bean definitions)

	@EnableAutoConfiguration (triggers the classpath-based auto-configuration mechanism )

	@ComponentScan (starts scanning for @Component classes from this package downward)

public class Application — a plain public class. Nothing special.
public static void main(String[] args) — standard Java entry point. Spring Boot apps are regular Java apps — they just delegate the work to SpringApplication.
SpringApplication.run(Application.class, args) — this single line does a lot:

	Creates a SpringApplication instance

	Deduces the application type (servlet-based, reactive, or none — here it will be NONE because there's no web starter)

	Sets up listeners and initializers

	Creates the ApplicationContext

	Loads all bean definitions (component scan + auto-config)

	Instantiates and wires all beans

	Publishes lifecycle events

	Returns — and the JVM stays alive as long as non-daemon threads exist (with no web server, this one will exit almost immediately, which is what we want for a "hello, container works" test)


If you were to remove the @SpringBootApplication the application will still start the ApplicationContext will still get created but the will be not autConfiguration, no component scan non of that

Changes after running the application

	Compared to Lesson 1, three things are now different:

	The log includes a line like:
	   Tomcat initialized with port 8080 (http)
	   ...
	   Tomcat started on port 8080 (http) with context path ''
	   Started Application in 1.234 seconds
	The JVM does not exit. In Lesson 1, main() returned and the process died. Now it stays running.
	If you open http://localhost:8080 in a browser, you get a Boot-generated 404 page (the "Whitelabel Error Page").

	Why did all this happen from one dependency change?

	The chain, in slow motion:

		Tomcat classes are on the classpath.

		SpringApplication.run() detects a servlet-based web app (because jakarta.servlet.Servlet and Tomcat are both present).

		It creates a AnnotationConfigServletWebServerApplicationContext — not the plain AnnotationConfigApplicationContext you had in Lesson 1.

		Auto-configuration processes ServletWebServerFactoryAutoConfiguration. Guarded by @ConditionalOnClass({ Servlet.class, Tomcat.class, ... }) — passes. Registers a TomcatServletWebServerFactory bean.

		Auto-configuration processes DispatcherServletAutoConfiguration. Guarded by @ConditionalOnClass(DispatcherServlet.class) — passes. Registers a DispatcherServlet bean.

		During context refresh(), the specialized web context sees the ServletWebServerFactory bean, calls getWebServer(...) on it (passing the DispatcherServlet as an initializer), receives a started TomcatWebServer, and Tomcat's non-daemon acceptor threads keep the JVM alive.

		The 404 is Spring MVC saying "I received your request, but I have no handler mapped for /."

	You didn't write any of that. You added one dependency; auto-configuration did the rest. This is the payoff of Lesson 1's concept #7 becoming visible.

2.@RestController 

This is a stereotype annotation — a specialized @Component. It marks the class as:
	A Spring bean (so component scan picks it up and Spring instantiates it).
	A web controller (so Spring MVC will look at its methods for request handlers).
	A "REST" controller — meaning method return values are written directly to the HTTP response body, not treated as view names.
	
	@RestController is essentially a combination of:
		@Controller
		@ResponseBody

	@Controller

		Tells Spring:

		"This class is a web controller."

		Spring will detect it during component scanning and create it as a Spring bean.

		@Controller (older) is for classic MVC where methods return a view name ("home") that a view resolver maps to a template (home.jsp, home.html). The rendered template becomes the response body.

		@RestController is for APIs that return data (JSON, XML, plain text). Spring skips view resolution entirely and serializes the return value using an HttpMessageConverter.

	@ResponseBody

		Tells Spring:

		"The value returned from this method should be written directly into the HTTP response body."

		For a String return type, Spring uses StringHttpMessageConverter and writes it as text/plain. For a POJO, it picks MappingJackson2HttpMessageConverter and writes it as application/json. (This is why spring-boot-starter-web bundles Jackson — it enables that conversion out of the box.)

		That's the important part for REST APIs.

	Why is @ResponseBody important?

		Consider:

		@Controller
		public class HelloController {

		    @GetMapping("/hello")
		    public String getHello() {
		        return "Hello";
		    }
		}

		With a regular @Controller, Spring traditionally interprets the returned String as a view name.

		It could think:

		"Hello"
		  ↓
		Find a view/template called "Hello"

		But with:

		@RestController

		Spring understands:

		"Hello"
		  ↓
		HTTP response body

		So:

		@RestController
		public class HelloController {

		    @GetMapping("/hello")
		    public String getHello() {
		        return "Hello";
		    }
		}

		produces:

		HTTP Response

		200 OK

		Hello


	@RestController doesnt define an endpoint 

	@RestController is a stereotype combining @Controller and @ResponseBody. It marks the class as a Spring-managed web controller whose method return values are serialized directly to the HTTP response body via HttpMessageConverters, rather than resolved as view names.

3.@RequestMapping

	@RequestMapping is the general-purpose mapping annotation.
		For example:
			@RequestMapping("/users")
			public class UserController {
			}

			This tells Spring:

			All mappings inside this controller start with /users.

			You can also use it on a method:

			@RequestMapping("/users")
			public List<User> getUsers() {
			    return users;
			}

			@RequestMapping(
		    value = "/users",
		    method = RequestMethod.GET
			)
			public List<User> getUsers() {
			    return users;
			}

4.@GetMapping("/hello")

	Two things happen here:

	HTTP method binding — this method handles only GET requests. A POST /hello would 405 (Method Not Allowed).
	Path binding — the path is /hello relative to the application's context path(context path takes plays when multiples app are deployed to the same server ) (empty by default, so the absolute URL is http://localhost:8080/hello).

	@GetMapping("/hello") is shorthand for @RequestMapping(path = "/hello", method = RequestMethod.GET). Same shortcuts exist for @PostMapping, @PutMapping, @DeleteMapping, @PatchMapping.

	@GetMapping is a composed annotation that specializes @RequestMapping for HTTP GET. Spring MVC's RequestMappingHandlerMapping scans beans annotated with @Controller/@RestController at startup, indexes their @*Mapping methods, and at request time picks the best match by path, HTTP method, headers, and content type.

	This handles:
		GET /users
		GET is normally used to retrieve data.
5.@PostMapping means:
	Handle HTTP POST requests.
	POST is commonly used to create something or submit data.
	Example:
	@PostMapping("/users")
	public User createUser(@RequestBody User user) {
	    return userService.createUser(user);
	}

	A client might send:

	POST /users

	with:

	{
	    "name": "John",
	    "age": 25
	}
6.@PutMapping handles HTTP PUT.

PUT is commonly used to replace/update an existing resource.
	@PutMapping("/users/{id}")
	public User updateUser(
	        @PathVariable Long id,
	        @RequestBody User user) {

	    return userService.updateUser(id, user);
	}

	Request:

	PUT /users/10

	Body:

	{
	    "name": "John",
	    "age": 30
	}
7.@PatchMapping handles HTTP PATCH.
	PATCH is generally used for a partial update.
	For example, suppose the user is:
	{
	    "name": "John",
	    "age": 25,
	    "email": "john@example.com"
	}

	You might want to change only the email:

	PATCH /users/10

	with:

	{
	    "email": "newjohn@example.com"
	}

	Unlike PUT, PATCH generally means:

	"Change these particular fields."
8.@DeleteMapping handles HTTP DELETE.

	It's normally used to delete a resource.

	@DeleteMapping("/users/{id}")
	public void deleteUser(@PathVariable Long id) {
	    userService.deleteUser(id);
	}

	Request:

	DELETE /users/10

	Spring calls:

	deleteUser(10)

The Process :

	Browser
	   │  types http://localhost:8080/hello
	   │
	   │  HTTP/1.1 GET /hello
	   │  Host: localhost:8080
	   │
	   ▼
	Embedded Tomcat
	   │  (running inside your JVM, same process as your beans)
	   │
	   ├── Acceptor thread on port 8080 accepts TCP connection
	   ├── Hands off to a worker thread from Tomcat's thread pool
	   │
	   ▼
	Servlet Container
	   │  parses HTTP into an HttpServletRequest
	   │  routes to the servlet mapped for the path
	   │  → the ONLY servlet registered is DispatcherServlet, mapped to "/"
	   │
	   ▼
	DispatcherServlet.service(request, response)
	   │  ← this is the "front controller" — everything goes through it
	   │
	   ├── 1. Ask HandlerMapping: "who handles GET /hello?"
	   │        RequestMappingHandlerMapping consults its indexed map
	   │        → returns HandlerMethod(HelloController#hello)
	   │
	   ├── 2. Ask HandlerAdapter: "how do I invoke this handler?"
	   │        RequestMappingHandlerAdapter resolves method arguments
	   │        (none needed here), invokes hello() via reflection
	   │        → gets back the String "Hello World"
	   │
	   ├── 3. Take the return value through HandlerMethodReturnValueHandler
	   │        Because the method is @ResponseBody (via @RestController),
	   │        RequestResponseBodyMethodProcessor kicks in
	   │
	   ├── 4. Pick an HttpMessageConverter based on:
	   │        - the method's return type (String)
	   │        - the Accept header from the client
	   │        → StringHttpMessageConverter
	   │
	   ├── 5. Write "Hello World" to the response body
	   │        Set Content-Type: text/plain;charset=UTF-8
	   │        Set Content-Length: 11
	   │
	   ├── (if anything went wrong: HandlerExceptionResolver picks it up)
	   │
	   ▼
	Tomcat writes the HTTP response back over the socket
	   │
	   ▼
	Browser renders "Hello World"

9.What is a DispatcherServlet?

	A DispatcherServlet is a servlet.

	It extends the Servlet API's HttpServlet and acts as a single entry point for Spring MVC HTTP requests.

	Instead of you creating:

	/hello  → HelloServlet
	/users  → UserServlet
	/orders → OrderServlet

	Spring typically has:

	/* → DispatcherServlet

	Then DispatcherServlet receives the request and decides which Spring controller method should handle it.

	So its job is basically:

	Receive an HTTP request → find the Spring method mapped to that request → invoke that method → turn the result into an HTTP response.

	1.Basic idea of a DispatcherServlet

		Forget Spring for a moment.

		A servlet can receive an HTTP request and decide what code should run based on:

		URL/path
		HTTP method (GET, POST, etc.)

		Example:

		HTTP Request
		     ↓
		MyDispatcherServlet
		     ↓
		Look at URL
		     ↓
		Look at HTTP method
		     ↓
		Decide what code should run

		For example:

		GET /hello

		The servlet checks:

		if (method.equals("GET") && path.equals("/hello"))

		and then runs the code for /hello.

		So basically, a dispatcher is responsible for figuring out which code should handle a request.

	2. Why not put everything inside the servlet?

		You could do something like:

		if (path.equals("/hello")) {
		    ...
		}

		if (path.equals("/users")) {
		    ...
		}

		if (path.equals("/orders")) {
		    ...
		}

		if (path.equals("/products")) {
		    ...
		}

		But obviously this gets messy.

		The servlet would eventually contain a huge amount of application logic.

		Spring doesn't want the DispatcherServlet to contain all of our business/application logic.

		Instead, we put the logic inside controllers.

		Example:

		@RestController
		public class HelloController {

		    @GetMapping("/hello")
		    public String hello() {
		        return "Hello You there";
		    }
		}

		Now the question becomes:

		GET /hello
		    ↓
		Which controller/method should run?

		That's where Handler Mappings come in.

	3. Handler Mapping

		Spring needs some kind of registry that keeps track of:

		HTTP method + URL
		        ↓
		method that should handle it

		Conceptually, imagine:

		Map<RequestMapping, HandlerMethod> mappings;

		Inside this map we could have:

		GET /hello
		    ↓
		HelloController.hello()

		GET /users
		    ↓
		UserController.getUsers()

		POST /users
		    ↓
		UserController.createUser()

		So when we write:

		@GetMapping("/hello")
		public String hello() {
		    return "Hello You there";
		}

		Spring finds this method during application startup and registers something conceptually like:

		mappings.put(
		    new RequestMapping("GET", "/hello"),
		    new HandlerMethod(helloController, "hello")
		);

		The important thing:

		The URL mapping isn't registered directly on the servlet.

		Instead, Spring's MVC infrastructure keeps track of these mappings.

		The DispatcherServlet later asks that infrastructure:

		"I received GET /hello. Who is supposed to handle this?"

	4. Simplified DispatcherServlet

		A very simplified version could look like:

		public class MyDispatcherServlet extends HttpServlet {

		    private Map<RequestMapping, HandlerMethod> mappings;

		    @Override
		    protected void service(
		            HttpServletRequest request,
		            HttpServletResponse response)
		            throws IOException {

		        String method = request.getMethod();
		        String path = request.getRequestURI();

		        HandlerMethod handler =
		            mappings.get(new RequestMapping(method, path));

		        if (handler == null) {
		            response.setStatus(404);
		            return;
		        }

		        Object result = handler.invoke();

		        response.getWriter().write(result.toString());
		    }
		}

		a more real DispatcherServlet would look like 

			protected void doDispatch(HttpServletRequest req, HttpServletResponse resp) {
			    HandlerExecutionChain handler = getHandler(req);              // HandlerMapping lookup
			    HandlerAdapter adapter = getHandlerAdapter(handler.getHandler());
			    applyPreHandleInterceptors(handler);
			    ModelAndView mv = adapter.handle(req, resp, handler.getHandler()); // invokes your method
			    applyPostHandleInterceptors(handler);
			    processDispatchResult(req, resp, handler, mv, exception);     // render view OR write body
			}

		DispatcherServlet is Spring MVC's front controller — a single HttpServlet that receives every request and delegates to HandlerMapping, HandlerAdapter, message converters, and exception resolvers. It exists so cross-cutting concerns like argument binding, view resolution, message conversion, and exception handling are centralized instead of duplicated per endpoint. In Spring Boot it's registered with the embedded container automatically by DispatcherServletAutoConfiguration using the Servlet 3.0 programmatic API


10.Content-Type tells Spring what format the request body is in, so Spring knows how to turn that body into Java values/objects.

	1. application/json — most common for REST APIs
		What the request looks like
		POST /users
		Content-Type: application/json

		Body:

		{
		  "name": "John",
		  "surname": "Smith"
		}
		Spring code

		Usually you create a DTO:

		public class UserRequest {
		    private String name;
		    private String surname;

		    // getters and setters
		}

		Then:

		@PostMapping
		public String registerUser(@RequestBody UserRequest user) {
		    return "Hello " + user.getName() + " " + user.getSurname();
		}
		What Spring does

		Conceptually:

		JSON
		   ↓
		Jackson
		   ↓
		UserRequest object
		   ↓
		registerUser(user)

		@RequestBody is basically telling Spring:

		"Take the request body and convert it into this Java object."

	2. application/x-www-form-urlencoded

		Very common with HTML forms.

		What the request looks like
		POST /users
		Content-Type: application/x-www-form-urlencoded

		Body:

		name=John&surname=Smith

		Think of it as:

		key=value&key=value&key=value
		Spring code

		You can simply do:

		@PostMapping
		public String registerUser(String name, String surname) {
		    return "Hello " + name + " " + surname;
		}

		Or explicitly:

		@PostMapping
		public String registerUser(
		        @RequestParam String name,
		        @RequestParam String surname) {

		    return "Hello " + name + " " + surname;
		}
		What Spring does
		name=John&surname=Smith
		          ↓
		Spring extracts parameters
		          ↓
		name = "John"
		surname = "Smith"
		          ↓
		registerUser(name, surname)

		Unlike JSON, you don't normally use @RequestBody here.

	3. multipart/form-data

		This is mainly used when you're sending files, often together with other fields.

		For example, uploading a profile picture.

		What it looks like

		It's more complicated internally:

		POST /users
		Content-Type: multipart/form-data; boundary=----12345

		Body is roughly:

		------12345
		Content-Disposition: form-data; name="name"

		John
		------12345
		Content-Disposition: form-data; name="surname"

		Smith
		------12345
		Content-Disposition: form-data; name="profilePicture"; filename="me.jpg"
		Content-Type: image/jpeg

		[binary image data]
		------12345--

		You normally don't manually construct this.

		Spring code
		@PostMapping
		public String registerUser(
		        @RequestParam String name,
		        @RequestParam String surname,
		        @RequestParam MultipartFile profilePicture) {

		    return "Hello " + name + " " + surname;
		}
		What Spring does
		multipart/form-data
		        ↓
		Spring separates the different parts
		        ↓
		name → String
		surname → String
		profilePicture → MultipartFile
		        ↓
		registerUser(...)

		This is the usual choice when uploading files.

	4. text/plain

		The body is simply plain text.

		Request
		POST /hello
		Content-Type: text/plain

		Body:

		Hello John
		Spring code
		@PostMapping
		public String hello(@RequestBody String message) {
		    return "Received: " + message;
		}

		Spring essentially gives you the body as a String.

		"Hello John"
		      ↓
		String
		      ↓
		@RequestBody String message
	5. text/html

		The body contains HTML.

		Request
		POST /page
		Content-Type: text/html

		Body:

		<h1>Hello John</h1>
		<p>Welcome!</p>
		Spring code

		You can read it as a String:

		@PostMapping
		public String receiveHtml(@RequestBody String html) {
		    return "Received HTML";
		}

		Although in normal Spring MVC applications, HTML is more commonly something Spring returns rather than something your API receives.

		For example:

		@GetMapping("/page")
		public String page() {
		    return "index";
		}

		With a template engine such as Thymeleaf, "index" refers to an HTML template.

	6. application/xml

		XML is another structured data format.

		Request
		POST /users
		Content-Type: application/xml

		Body:

		<user>
		    <name>John</name>
		    <surname>Smith</surname>
		</user>

		Spring can convert this into a Java object if the appropriate XML message converter/configuration is available.

		Conceptually:

		@PostMapping
		public String registerUser(@RequestBody UserRequest user) {
		    return "Hello " + user.getName();
		}

		The important part is:

		@RequestBody UserRequest user

		Spring's message conversion infrastructure handles the conversion.

		So:

		XML
		 ↓
		XML message converter
		 ↓
		UserRequest
		 ↓
		controller

		JSON works similarly:

		JSON
		 ↓
		Jackson
		 ↓
		UserRequest
		 ↓
		controller
	7. application/octet-stream

		This basically means:

		"Here is some arbitrary binary data."

		For example:

		PDF
		ZIP
		image
		binary file
		etc.

		Request:

		POST /upload
		Content-Type: application/octet-stream

		Body:

		[binary data]
		Spring code

		You could receive it as bytes:

		@PostMapping
		public String upload(@RequestBody byte[] data) {
		    System.out.println(data.length);
		    return "Uploaded";
		}
11.The conection between Http and Spring 
	
	There are three different things you should keep separate in your head:

	1. HTTP method
		POST

		Answers:

		What are we trying to do with the resource?

	2. URL
		/users

		Answers:

		Which resource/endpoint are we talking to?

	3. Content-Type
		Content-Type: application/json

		Answers:

		What format is the request body in?

		So a complete request could be:

		POST /users
		Content-Type: application/json

		{
		    "name": "John",
		    "surname": "Smith"
		}

		And Spring sees:

		POST
		 ↓
		@PostMapping

		/users
		 ↓
		@RequestMapping("/users")

		application/json
		 ↓
		Jackson / HttpMessageConverter

		JSON
		 ↓
		UserRequest

		@RequestBody UserRequest
		 ↓
		registerUser(...)

		This is the connection between HTTP and the Spring controller method.

12.In Spring MVC, request parameter annotations are annotations you put on controller method arguments to tell Spring where to get values from the incoming HTTP request.
	
	The most important ones are:
		@PathVariable
		@RequestParam
		@RequestBody
		@RequestHeader
		@CookieValue

	1. @RequestParam

		Suppose the client sends:

		GET /users?name=john&age=25

		The values:

		name=john
		age=25

		are query parameters.

		You can access them with @RequestParam:

		@GetMapping("/users")
		public String getUser(
		        @RequestParam String name,
		        @RequestParam int age) {

		    return name + " " + age;
		}

		Spring sees:

		GET /users?name=john&age=25

		and essentially does:

		name → "john"
		age  → 25

		Then your method receives:

		getUser("john", 25)

		@RequestParam(
			defaultValue ="default" // can provide default values;
			required = false  // a requestparam is required true by default 
		)
	2.@PathVariable

		Consider:

			GET /users/25

			Here 25 is part of the URL path.

			You would use:

			@GetMapping("/users/{id}")
			public User getUser(@PathVariable Long id) {
			    ...
			}

			Spring maps:

			/users/{id}
			       ↓
			/users/25
			       ↓
			id = 25

			So:

			/users/25
	3.@RequestBody

		Now consider a POST request:

		POST /users

		with JSON:

		{
		    "name": "John",
		    "age": 25
		}

		The data isn't in the URL.

		It's in the HTTP request body.

		So you use:

		@PostMapping("/users")
		public User createUser(@RequestBody User user) {
		    ...
		}

		Spring takes the JSON:

		{
		    "name": "John",
		    "age": 25
		}

		and converts it into:

		User

		Conceptually:

		JSON request body
		       ↓
		@RequestBody
		       ↓
		Java User object

		This conversion is handled by Spring's HTTP message conversion infrastructure.

	4.@RequestHeader

		HTTP requests also contain headers.

		For example:

		GET /users

		Authorization: Bearer abc123
		Accept: application/json

		You can access a header using:

		@GetMapping("/users")
		public String getUsers(
		        @RequestHeader("Authorization") String authorization) {

		    return authorization;
		}

		Spring extracts:

		Authorization: Bearer abc123

		and gives your method:

		authorization = "Bearer abc123"
	5.@CookieValue

	You can also get values from cookies:

		@GetMapping("/profile")

		Cookie: sessionId=abc123

	private final HelloService helloService; — final is possible only because we're using constructor injection. This is one of the reasons it's preferred.

	What Spring Actually Did
	------------------------

		1.  SpringApplication.run(Application.class)

		2.  Create ApplicationContext (AnnotationConfigServletWebServerApplicationContext)

		        │

		        │
		        ▼

		        │  Iterates all non-lazy singleton bean definitions and calls getBean(name) on each
		        │

		        │      → find constructor: HelloController(HelloService)

		        │              → find candidate bean definitions matching HelloService

	What a BeanDefinition Actually Is
	---------------------------------

		public interface BeanDefinition {
		    String getBeanClassName();      // "com.example.auth.hello.HelloService"
		    String getScope();              // "singleton"
		    boolean isLazyInit();           // false
		    boolean isPrimary();            // false
		    ConstructorArgumentValues getConstructorArgumentValues();
		    MutablePropertyValues getPropertyValues();
		    String getFactoryMethodName();  // for @Bean methods, this points to the factory method
		    String getInitMethodName();
		    String getDestroyMethodName();
		    // ...
		}

		Component scan creates one of these per discovered @Component. @Bean methods create one per method. XML <bean> elements create one per element. All roads lead to BeanDefinition.

		This matters because it explains a lot of behavior:
		---------------------------------------------------

			1.You can inspect and modify definitions before beans are instantiated (that's what BeanFactoryPostProcessor does).

			2.You can register a bean definition programmatically at any point during context configuration — no annotation required.

			3.Boot's auto-configuration works entirely at the BeanDefinition level; the "conditional" checks are checks against the current set of definitions.

		"A BeanDefinition is metadata describing how Spring should create and configure a bean — class name, scope, constructor arguments, init/destroy methods, autowire mode. Component scan, @Bean methods, and XML are just different ways of producing BeanDefinitions. Instantiation happens later, driven by these definitions."


	The Four Stereotypes: @Component, @Service, @Repository, @Controller
	--------------------------------------------------------------------

		@Target({ElementType.TYPE})
		@Retention(RetentionPolicy.RUNTIME)
		@Component        // ← literally
		public @interface Service {
		    @AliasFor(annotation = Component.class)
		    String value() default "";
		}
		Note : All four register a bean the same way, via component scan, at the same time.

		So why have four?
		-----------------

			1.@Component : Generic bean stereotype

			2.@Service : Semantic: "this is a service-layer class" this annotation is not different from @Component

			3.@Controller : recognized by RequestMappingHandlerMapping as a source of web handlers : in simple terms this one is also recognized by Spring MVC 

			4.@Repository : triggers exception translation (JPA/Hibernate exceptions → Spring's DataAccessException 				hierarchy)

		So:
		--

			@Service is purely documentation. Removing @Service and using @Component would work identically.
			
			@Controller adds a real behavior (handler mapping notices it). Remove it and the controller silently stops handling requests.
			
			@Repository adds exception translation (via a BeanPostProcessor called PersistenceExceptionTranslationPostProcessor). Remove it and JPA exceptions leak through untranslated. We'll come back to this at Stage 7.

		"All four are stereotypes that register a bean via component scan; underneath, @Service, @Repository, and @Controller are all meta-annotated with @Component. @Service is purely semantic. @Controller is functionally different — it's what makes Spring MVC's handler mapping recognize the class. @Repository adds exception translation to Spring's DataAccessException hierarchy."


	Constructor vs Setter vs Field Injection
	----------------------------------------


		+-----------------------------------------------+-------------+--------+-------+
		| Property                                      | Constructor | Setter | Field |
		+-----------------------------------------------+-------------+--------+-------+
		| Fields can be final (truly immutable)         |     YES     |   NO   |  NO   |
		| Object cannot exist half-constructed          |     YES     |   NO   |  NO   |
		| Trivially testable without Spring             |     YES     |   YES  |  NO   |
		| Circular dependencies fail loudly at startup  |     YES     |   NO   |  NO   |
		| Too many dependencies become obvious          |     YES     |   NO   |  NO   |
		| Works without Spring at all                   |     YES     |   YES  |  NO   |
		+-----------------------------------------------+-------------+--------+-------+

		The circular-dependency point is the interview trap. With setter or field injection, Spring can create bean A partially, then bean B, then finish A. Circles are silently resolved. With constructor injection, Spring can't — A can't be constructed without B, and B can't be constructed without A. The startup fails with BeanCurrentlyInCreationException, forcing you to fix the design.

		"Constructor injection is preferred because dependencies become immutable (final), the object is always fully initialized, circular dependencies fail loudly at startup instead of being silently patched, and the class is testable with plain new — no Spring or reflection required. Field injection breaks all four of those properties, which is why it's discouraged in production code."


	What If There Are Multiple Candidates?
	---------------------------------------

		public interface Greeter {
		    String greet(String name);
		}

		@Service class FormalGreeter implements Greeter { ... }
		@Service class CasualGreeter implements Greeter { ... }

		@RestController
		class HelloController {
		    HelloController(Greeter greeter) { ... }   // which one?!
		}

		Spring resolves ambiguity in this order:
		----------------------------------------

			1.@Primary on one of the beans — that one wins.
			   @Service @Primary class FormalGreeter implements Greeter { ... }

			2.@Qualifier at the injection point — explicit selection.
			   HelloController(@Qualifier("casualGreeter") Greeter greeter) { ... }

			3.Parameter name match — if the constructor parameter is named casualGreeter, Spring matches by bean name. (Requires debug info in the compiled bytecode; Boot's default compile settings include it.)

			If none of those disambiguate, Spring throws NoUniqueBeanDefinitionException at startup.


		You can also inject all implementations at once:

			HelloController(List<Greeter> greeters) { ... }   // gets both
			HelloController(Map<String, Greeter> greeters) { ... }  // beanName → instance

		This is the pattern for strategy/plugin architectures.

		"Spring resolves multiple candidates in order: @Primary, then @Qualifier, then parameter name. If none disambiguate, startup fails with NoUniqueBeanDefinitionException. You can also inject all candidates as List<T> or Map<String, T>."


	Bean Scopes
	-----------

		By default, every bean is a singleton — one instance per ApplicationContext, shared across every injection point. Not "singleton" in the Gang-of-Four sense (that's per-JVM); this is per-container.


		The scopes:
		-----------

			+-----------------+----------------------------+------------------------------------------------+
			| Scope           | Instances                  | When to use                                    |
			+-----------------+----------------------------+------------------------------------------------+
			| singleton       | One per container          | Almost everything — services, repositories,    |
			| (default)       |                            | controllers, config                            |
			| prototype       | New instance per injection | Stateful helpers you want fresh each time      |
			|                 | / getBean call             |                                                |
			| request         | One per HTTP request       | Request-scoped state (rare; prefer method      |
			| (web only)      |                            | parameters)                                    |
			| session         | One per HTTP session       | Session-scoped state (rare in stateless APIs)  |
			| (web only)      |                            |                                                |
			| application     | One per ServletContext     | Basically singleton for web apps               |
			| websocket       | One per WebSocket session  | Niche                                          |
			+-----------------+----------------------------+------------------------------------------------+


			The gotcha: if a singleton depends on a prototype, the prototype is created once and then reused — because the singleton is created once. To get fresh prototypes on every use, you need @Lookup, ObjectProvider<T>, or a scoped proxy. Same problem applies for injecting a request-scoped bean into a singleton. This trips people up in interviews.

			Interview answer: "Beans default to singleton scope — one instance per ApplicationContext, shared across injection points. Other scopes are prototype (new instance per lookup) and web scopes: request, session, application, websocket. Injecting a shorter-scoped bean into a longer-scoped one requires a scoped proxy or ObjectProvider, otherwise the shorter-scoped instance is captured once and reused."

	13.IoC, Beans, ApplicationContext & Dependency Injection
		
		1. What is IoC?

			IoC = Inversion of Control

			The basic idea is:

			Instead of our code creating and managing the objects it needs, Spring does it for us.

			Without Spring, we usually control things ourselves.

			With Spring, Spring takes over that responsibility.

		2. Normal Java — we create the objects ourselves

			For example:

			public class UserService {

			    public void register() {
			        System.out.println("Registering user");
			    }
			}

			And:

			public class UserController {

			    private UserService userService;

			    public UserController() {
			        this.userService = new UserService();
			    }

			    public void register() {
			        userService.register();
			    }
			}

			The important line is:

			this.userService = new UserService();

			UserController is creating its own dependency.

			So the relationship is:

			UserController
			      │
			      │ creates
			      ↓
			UserService

			The controller is in control of creating UserService.

		3. Now Spring takes over

			With Spring, we can write:

			@Service
			public class UserService {

			    public void register() {
			        System.out.println("Registering user");
			    }
			}

			And:

			@RestController
			public class UserController {

			    private final UserService userService;

			    public UserController(UserService userService) {
			        this.userService = userService;
			    }

			    public void register() {
			        userService.register();
			    }
			}

			Notice there is no:

			new UserService();

			inside UserController.

			So where does the UserService come from?

			Spring creates it and gives it to UserController.

			That's IoC.

		4. What exactly has been "inverted"?

			Before Spring:

			Your code
			   │
			   ├── creates UserController
			   ├── creates UserService
			   └── connects them

			With Spring:

			Spring
			   │
			   ├── creates UserController
			   ├── creates UserService
			   └── connects them

			So the control has moved from:

			Your code
			    ↓
			Spring

			That's the "inversion" in Inversion of Control.

		5. What is a Bean?

			A bean is basically an object that Spring creates and manages.

			For example:

			@Service
			public class UserService {
			}

			Spring sees @Service and thinks roughly:

			"I found this class.
			I should create an object from it
			and manage that object."

			Conceptually:

			UserService userService = new UserService();

			Spring then manages that object.

			That object is called a Spring bean.

			So:

			Class
			 ↓
			@Service
			 ↓
			Spring discovers it
			 ↓
			Spring creates an object
			 ↓
			That object becomes a Spring bean


		6. @Controller, @Service, @Repository

			These annotations tell Spring that a class should be discovered and managed as a bean.

			For example:

			@Service
			public class UserService {
			}
			@Repository
			public class UserRepository {
			}
			@Controller
			public class UserController {
			}

			And:

			@RestController
			public class UserController {
			}

			@RestController is also a Spring-managed component.

			So don't think:

			"@Service magically creates an object."

			A better way to think about it is:

			"@Service makes the class eligible for Spring's component scanning, and Spring can then create and manage an instance of that class as a bean."

		7. What is the ApplicationContext?

			Now we have a problem.

			If Spring is responsible for creating and managing all these objects...

			Where does Spring keep track of them?

			This is where the ApplicationContext comes in.

			The ApplicationContext is basically Spring's container for the application.

			A useful mental model is:

			ApplicationContext
			       │
			       ├── UserController
			       ├── UserService
			       ├── UserRepository
			       └── ...

			You can think of it like a big place where Spring keeps track of the beans it manages.

		8. Very simplified ApplicationContext

			Imagine we created our own tiny version of Spring:

			public class MyApplicationContext {

			    private Map<String, Object> beans = new HashMap<>();

			    public void register(String name, Object object) {
			        beans.put(name, object);
			    }

			    public Object getBean(String name) {
			        return beans.get(name);
			    }
			}

			Then:

			MyApplicationContext context =
			        new MyApplicationContext();

			UserService userService =
			        new UserService();

			context.register("userService", userService);

			Now conceptually:

			ApplicationContext
			       │
			       └── "userService"
			                ↓
			          UserService object

			Later, you could ask:

			UserService service =
			    (UserService) context.getBean("userService");

			Basically:

			"Give me the UserService object that you're managing."

			And the context gives it to you.

		9. The real ApplicationContext does much more

			The real ApplicationContext isn't just a simple Map.

			It is responsible for a lot of Spring's infrastructure.

			Some of the important things include:

			ApplicationContext
			       │
			       ├── Bean creation
			       ├── Dependency Injection
			       ├── Bean lifecycle
			       ├── Configuration
			       ├── Component scanning
			       ├── Events
			       ├── Application properties
			       └── other Spring infrastructure

			So a good mental model is:

			                 ApplicationContext
			                        │
			          ┌─────────────┼─────────────┐
			          ↓             ↓             ↓
			        Beans      Configuration   Infrastructure
			          │
			          ├── UserController
			          ├── UserService
			          ├── UserRepository
			          └── ...
		10. How does Spring find these classes?

			This is where things like:

			@Component
			@Service
			@Repository
			@Controller
			@RestController

			come into play.

			Suppose we have:

			@Service
			public class UserService {
			}
			@Repository
			public class UserRepository {
			}
			@RestController
			public class UserController {

			    private final UserService userService;

			    public UserController(UserService userService) {
			        this.userService = userService;
			    }
			}

			When the application starts, roughly speaking:

			Spring Boot starts
			       ↓
			ApplicationContext created
			       ↓
			Component scanning
			       ↓
			Find @Service
			       ↓
			Create UserService
			       ↓
			Find @Repository
			       ↓
			Create UserRepository
			       ↓
			Find @RestController
			       ↓
			Create UserController
			       ↓
			Inject UserService into UserController

			Eventually the context has something like:

			ApplicationContext
			│
			├── UserService
			│
			├── UserRepository
			│
			└── UserController
			       │
			       └── UserService
		11. This is where Dependency Injection comes in

			IoC and DI are closely related.

			Look at:

			public class UserController {

			    private final UserService userService;

			    public UserController(UserService userService) {
			        this.userService = userService;
			    }
			}

			UserController depends on UserService.

			That's why we call UserService a dependency.

			Without Spring, you might do:

			public UserController() {
			    this.userService = new UserService();
			}

			The controller creates its own dependency.

			With Spring:

			public UserController(UserService userService) {
			    this.userService = userService;
			}

			The controller basically says:

			"I need a UserService."

			Spring says:

			"Okay, here you go."

		12. The Dependency Injection process

			Conceptually:

			Spring creates UserService
			        ↓
			Spring creates UserController
			        ↓
			Spring sees UserController needs UserService
			        ↓
			Spring passes UserService into constructor

			So:

			UserController
			      │
			      │ needs
			      ↓
			UserService

			And Spring connects them.

			That's Dependency Injection.

		13. IoC vs Dependency Injection

			These are related, but they aren't exactly the same thing.

			IoC

			IoC is the big/general idea:

			The framework takes control of creating and managing objects instead of your application code doing it.

			Dependency Injection

			DI is one way of achieving IoC.

			It means:

			Instead of an object creating its own dependencies, the dependencies are provided to it.

			So you can think of it like:

			IoC
			 │
			 └── Dependency Injection

			Or:

			IoC = the overall principle

			DI = one technique Spring uses to implement that principle

Lesson 5 (Databases, JDBC, and Connection Pools)
------------------------------------------------


	Every single row of data your app ever reads flows through this stack. JPA/Hibernate don't bypass JDBC — they generate JDBC calls under the hood. Spring Data JPA doesn't bypass Hibernate — it generates method implementations that call into it. The abstractions stack; they don't replace.

	"JPA is a specification; Hibernate is an implementation of that specification; Spring Data JPA is a layer on top of JPA that generates repository implementations from interfaces. All three ultimately produce JDBC calls, which the vendor-specific JDBC driver turns into the database's wire protocol."


	Relational Database Primer
	--------------------------

		A relational database stores data in tables — a table is a set of rows, each row having the same columns. Each column has a type (text, integer, timestamp, boolean, etc.).

		The things that matter for our app:
		-----------------------------------

			1.Primary key — one or more columns that uniquely identify a row. For users, that's typically an id column. The DB enforces uniqueness.
			
			2.Foreign key — a column that refers to a primary key in another table. If orders has a user_id, that's a foreign key referencing users(id). The DB enforces that the referenced row exists.
			
			3.Index — a secondary data structure the DB maintains to speed up lookups on specific columns. Without an index on users.email, "find user by email" scans every row. With one, it's roughly O(log n). Primary keys are indexed automatically.
			
			4.Constraints — rules the DB enforces: NOT NULL, UNIQUE, CHECK (age >= 0), foreign keys. The database rejects writes that violate them.
			
			5.Transactions — a group of statements treated as one atomic unit. Either all succeed or none do. (We'll do transactions properly at Stage 8.)
			
			6.ACID — Atomicity (all-or-nothing), Consistency (constraints hold), Isolation (concurrent transactions don't see each other's partial work), Durability (committed data survives crashes).

	JDBC(Java Database Connectivity)
    --------------------------------

    	It's a Java API in the java.sql package, standardized as part of Java SE. It is not Spring, and it is not vendor-specific.


    	The core interfaces:

			1.java.sql.DataSource     // factory for Connections
			
			2.java.sql.Connection     // an open connection to the database
			
			3.java.sql.Statement      // a SQL statement (prefer PreparedStatement)
			
			4.java.sql.PreparedStatement  // a parameterized SQL statement
			
			5.java.sql.ResultSet      // the rows returned by a query





	Here is a complete JDBC query, written by hand with no Spring:
	--------------------------------------------------------------

		import java.sql.*;
		import javax.sql.DataSource;

		public class RawJdbcExample {

		    private final DataSource dataSource;

		    public RawJdbcExample(DataSource dataSource) {
		        this.dataSource = dataSource;
		    }

		    public String findEmailById(long id) throws SQLException {
		        String sql = "SELECT email FROM users WHERE id = ?";

		        try (Connection conn = dataSource.getConnection();
		             PreparedStatement stmt = conn.prepareStatement(sql)) {

		            stmt.setLong(1, id);

		            try (ResultSet rs = stmt.executeQuery()) {
		                if (rs.next()) {
		                    return rs.getString("email");
		                }
		                return null;
		            }
		        }
		    }
		}

	The dance:
		
		1.dataSource.getConnection() — borrow a connection (from a pool, in practice).
		
		2.conn.prepareStatement(sql) — ask the driver to prepare the SQL. The ? placeholders are bind parameters — this is how we avoid SQL injection.
		
		3.stmt.setLong(1, id) — bind the parameter. Note indices are 1-based, not 0-based. JDBC was written in 1997, back when some SQL dialects were 1-indexed.
		
		4.stmt.executeQuery() — the driver sends the SQL + parameters to the database.
		
		5.rs.next() — advance the cursor to the next row; returns false if there are no more.
		
		6.rs.getString("email") — pull a column by name (or by index — rs.getString(1)).
		
		7.All the try-with-resources blocks — JDBC resources must be closed. A missed close is a connection leak that will eventually exhaust the pool and freeze your app.


	Why PreparedStatement and not Statement
	---------------------------------------

		Don't do this:

			java
			String sql = "SELECT email FROM users WHERE id = " + id;  // DANGER

			Even for integer parameters this is a reflex you want to kill now. With user-controlled input it becomes catastrophic:

			java
			String sql = "SELECT * FROM users WHERE email = '" + userInput + "'";
			// userInput = "' OR '1'='1"  →  returns every user
			// userInput = "'; DROP TABLE users; --"  →  table gone

		PreparedStatement binds parameters outside the SQL string. The driver sends the SQL template and the parameters as separate things over the wire. The database parses the SQL once and treats the parameters as opaque values — they can never be interpreted as SQL. SQL injection becomes architecturally impossible.

		Second benefit: the database caches the parsed query plan for the SQL template, so repeated calls with different parameter values skip the parse step.

		JDBC is Java's standard database API in java.sql. The core types are DataSource (connection factory), Connection, PreparedStatement (parameterized SQL), and ResultSet (query results). Always use PreparedStatement with bind parameters, not string concatenation — it's immune to SQL injection and benefits from query plan caching.

	JDBC Drivers
	------------

		JDBC itself is just interfaces. Doing something useful requires an implementation — a driver — that knows how to talk to a specific database.

		For PostgreSQL: the org.postgresql:postgresql jar on Maven Central. It contains classes like org.postgresql.Driver and org.postgresql.jdbc.PgConnection that implement java.sql.Driver and java.sql.Connection respectively.

		How the driver gets wired in:
		-----------------------------

			1.Historically, you called Class.forName("org.postgresql.Driver") to force-load the driver class, which registered itself via a static initializer with java.sql.DriverManager.
			
			2.Since JDBC 4.0 (Java 6+), drivers register themselves automatically via the Service Provider Interface — they ship a file at META-INF/services/java.sql.Driver that names the driver class. Just having the jar on the classpath is enough.

		When you call dataSource.getConnection() on a vendor-neutral DataSource, it uses a URL like:

		jdbc:postgresql://localhost:5432/auth

		The URL's second segment (postgresql) is matched against registered drivers. The matching driver opens a TCP socket to localhost:5432, performs PostgreSQL's startup handshake, authenticates, and hands back a PgConnection that satisfies the java.sql.Connection interface.

		This is why you can swap databases. Change the driver jar, change the URL, and most of your JDBC code keeps working — because it was written against java.sql.Connection, not PgConnection. Vendor-specific features (PostgreSQL JSONB, ARRAY types, COPY) break this portability, but basic CRUD is portable.


	Connections and Why They Need a Pool
	------------------------------------

		Opening a database connection is expensive. For PostgreSQL, each connection costs roughly:

			A TCP handshake (3 round trips)
			
			A TLS handshake if encrypted (another 2 round trips)
			
			Authentication (1–3 round trips depending on method)
			
			PostgreSQL spawns a new OS process per connection (not a thread — a process)
			
			Per-connection memory on the server, typically multiple MB

		Opening a connection takes tens to hundreds of milliseconds. If every HTTP request opened a new connection, your app would be unusable at any real load.

		The solution is a connection pool: a long-lived set of connections created at startup, lent out to code that needs one, and returned to the pool when done.

		┌─────────────────────────────────────────┐
		│  HikariPool                             │
		│  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐        │
		│  │Conn1│ │Conn2│ │Conn3│ │Conn4│  ...   │
		│  └─────┘ └─────┘ └─────┘ └─────┘        │
		│  idle    in-use  idle    in-use         │
		└─────────────────────────────────────────┘
		         ▲             │
		         │             │
		    returned          borrowed
		         │             │
		         │             ▼
		    ┌──────────────────────────┐
		    │  Application thread      │
		    │  dataSource.getConnection│
		    │  → use → close           │
		    └──────────────────────────┘

		Note conn.close() does not close the physical connection — the pool intercepts it and returns the connection to the idle set. This is why try-with-resources is still correct even with a pool.

		Spring Boot's default pool is HikariCP — a very fast, battle-hardened implementation. Added automatically when you include any JDBC/JPA starter. Configuration lives under spring.datasource.hikari.* properties.

		Key parameters you'll touch in production:
		------------------------------------------

			properties
			spring.datasource.hikari.maximum-pool-size=10
			
			spring.datasource.hikari.minimum-idle=10
			
			spring.datasource.hikari.connection-timeout=30000
			
			spring.datasource.hikari.idle-timeout=600000
			
			spring.datasource.hikari.max-lifetime=1800000
		
		maximum-pool-size — hard ceiling on concurrent connections. Default is 10, which is often correct. More is not better; most apps are DB-bound long before thread-count-bound. HikariCP's own docs make this point explicitly.
		connection-timeout — how long a thread waits for a connection before failing. If all connections are in use and the pool is at max, requests queue; after this timeout, SQLTransientConnectionException.
		max-lifetime — connections are retired after this age even if healthy, defending against DB-side resource leaks and firewall idle kills.

		The "max connections = CPU count" instinct is wrong for DBs. Connections map to DB-side work (processes in PG, threads in MySQL), and the DB has its own concurrency limits. Over-sizing the pool makes things worse by stacking contention inside the database.

		Interview-ready: "A JDBC connection is expensive to open — TCP, TLS, auth, and a server-side process in PostgreSQL. A connection pool keeps a warm set of connections and lends them out. conn.close() returns to the pool; it doesn't disconnect physically. Spring Boot uses HikariCP by default. Pool sizing is about matching DB-side capacity, not application concurrency; 10 is often correct."



	DataSource
	----------

		javax.sql.DataSource is JDBC's abstraction for "something that produces connections." A connection pool implements it. A raw JDBC driver also provides a basic implementation. Your application code depends on DataSource and does not know (and should not care) whether a pool sits behind it.

		In a Spring Boot app you never construct a DataSource by hand. When you add spring-boot-starter-jdbc (or JPA, which brings JDBC along), DataSourceAutoConfiguration fires:

		Reads spring.datasource.* properties.
		Looks at the classpath — HikariCP is present via spring-boot-starter-jdbc.
		Builds and configures a HikariDataSource bean.
		Registers it as the DataSource bean in the context.

		Any component that injects DataSource gets Hikari. You could override by defining your own @Bean DataSource — @ConditionalOnMissingBean would skip the auto-config. The pattern you've seen before.


	Add Dependencies
	----------------

		<dependencies>
		    <dependency>
		        <groupId>org.springframework.boot</groupId>
		        <artifactId>spring-boot-starter-web</artifactId>
		    </dependency>

		    <!-- NEW: Spring JDBC + HikariCP via Boot -->
		    <dependency>
		        <groupId>org.springframework.boot</groupId>
		        <artifactId>spring-boot-starter-jdbc</artifactId>
		    </dependency>

		    <!-- NEW: PostgreSQL driver (runtime scope — not needed at compile time) -->
		    <dependency>
		        <groupId>org.postgresql</groupId>
		        <artifactId>postgresql</artifactId>
		        <scope>runtime</scope>
		    </dependency>
		</dependencies>

		Note <scope>runtime</scope> on the PostgreSQL driver. We don’t compile against driver-specific types — only java.sql.* and javax.sql.*. The driver only needs to be on the classpath at runtime so JDBC can find it. This is good discipline that keeps your code portable.

		Maven’s runtime scope means a dependency isn’t visible during compilation but is included in runtime and test classpaths. It’s correct for JDBC drivers because application code depends on java.sql.* interfaces, not vendor-specific classes — the driver is only discovered via SPI at runtime.


	Configure the DataSource
	------------------------

		# Database connection
		spring.datasource.url=jdbc:postgresql://localhost:5432/auth
		spring.datasource.username=authapp
		spring.datasource.password=devpass
		spring.datasource.driver-class-name=org.postgresql.Driver

		# Hikari pool
		spring.datasource.hikari.maximum-pool-size=10
		spring.datasource.hikari.minimum-idle=2

		spring.datasource.hikari.pool-name=AuthHikariPool

		# SQL logging — useful while learning, remove in production
		logging.level.org.springframework.jdbc.core.JdbcTemplate=DEBUG


		A few points worth understanding:
		---------------------------------

			spring.datasource.driver-class-name is optional. Boot can usually infer the driver from the URL (jdbc:postgresql:// → org.postgresql.Driver). I’ve included it so you see it exists.

			The URL format jdbc:postgresql://host:port/database is a JDBC convention — every driver has its own URL dialect. MySQL: jdbc:mysql://.... Oracle: jdbc:oracle:thin:@.... Learn to read these.

			pool-name only matters for debugging — appears in logs and JMX. Setting it saves confusion later.

			Credentials in application.properties are not production practice. We’ll cover externalization at Stage 17. For now, local dev credentials in a git-ignored file is fine.

		YAML alternative
		----------------

			spring:
			  datasource:
			    url: jdbc:postgresql://localhost:5432/auth
			    username: authapp
			    password: devpass
			    hikari:
			      maximum-pool-size: 10
			      pool-name: AuthHikariPool

		Properties and YAML are interchangeable; Spring Boot reads both. YAML is denser for deep nesting; properties are simpler for flat config. Pick one and stick to it per project.

	Externalized Configuration, Briefly
	-----------------------------------

		Everything in application.properties is externalized configuration. Spring Boot reads it from, in increasing priority order:

			1.application.properties / application.yml baked into the jar
			
			2.application-{profile}.properties for an active profile
			
			3.External application.properties next to the jar
			
			4.OS environment variables (SPRING_DATASOURCE_URL)
			
			5.JVM system properties (-Dspring.datasource.url=...)
			
			6.Command-line arguments (--spring.datasource.url=...)

		The property-key-to-environment-variable mapping is:
		spring.datasource.url → SPRING_DATASOURCE_URL (dots → underscores, uppercase).

		This is why containerized apps work. The same jar runs in dev, staging, and prod — only the env vars differ. Credentials never ship in the jar. You get this for free from Boot; you just need to use it.

		Spring Boot reads configuration from application.properties/.yml, profile-specific files, external files, environment variables, system properties, and command-line arguments, in that priority order. Env vars map by uppercasing and replacing dots with underscores. This is what makes a Boot jar portable across environments.










































































































































































14.Validation in Spring MVC

	1. What is Bean Validation?

		Spring MVC has built-in support for Jakarta Bean Validation.

		The basic idea is:

		We put validation rules on our Java object, and Spring checks those rules before the controller method runs.

		For example:

		@NotBlank
		String username

		means:

		Username cannot be blank.

		Instead of writing lots of if statements ourselves, we declare the rules and let the validation system check them.

	3. Create a request DTO

		It's usually better not to put these validation rules directly on your User entity.

		Instead, create a class specifically for the data the client is allowed to send.

		For example:

		public record RegistrationRequest(

		        @NotBlank(message = "Username is required")
		        @Size(
		            min = 5,
		            max = 20,
		            message = "Username must be between 5 and 20 characters"
		        )
		        String username,

		        @NotBlank(message = "Email is required")
		        @Email(message = "Email address is invalid")
		        String email,

		        @NotBlank(message = "Password is required")
		        @Size(
		            min = 8,
		            message = "Password must be at least 8 characters"
		        )
		        String password

		) {}

		Now the validation rules live next to the data they're describing.

		For example:

		@Size(min = 8)
		String password

		basically means:

		Password must be at least 8 characters long.

		So instead of:

		if (password.length() < 8) {
		    ...
		}

		we just declare:

		@Size(min = 8)

		and Bean Validation handles the checking.

	4. What do these annotations mean?

		Some common ones:

		@NotBlank

		The value cannot be null, empty, or just whitespace.

		@Size(min = 5, max = 20)

		The value must be between 5 and 20 characters/items, depending on the type.

		@Email

		The value should have a valid email format.

		So our request object is basically saying:

		RegistrationRequest
		│
		├── username
		│     ├── required
		│     └── 5–20 characters
		│
		├── email
		│     ├── required
		│     └── valid email format
		│
		└── password
		      ├── required
		      └── at least 8 characters
	6. What happens when the data is valid?

		The controller method gets to run normally.

	7. What happens when the data is invalid?

		Now suppose the client sends:

		{
		    "username": "ab",
		    "email": "hello",
		    "password": "123"
		}

		Spring first creates the object:

		RegistrationRequest
		│
		├── username = "ab"
		├── email = "hello"
		└── password = "123"

		Then validation runs.

		Username
		"ab"
		 ↓
		@Size(min = 5)
		 ↓
		❌ Invalid
		Email
		"hello"
		 ↓
		@Email
		 ↓
		❌ Invalid
		Password
		"123"
		 ↓
		@Size(min = 8)
		 ↓
		❌ Invalid

		Spring finds all these validation failures.

		You don't have to write:

		if (username.length() < 5) {
		    ...
		}

		if (!email.contains("@")) {
		    ...
		}

		if (password.length() < 8) {
		    ...
		}

		That's the whole point of Bean Validation.

	8. What happens to the controller?

		This is important.

		If validation fails, the controller method doesn't continue normally.

		Instead:

		HTTP request
		     ↓
		@RequestBody
		     ↓
		RegistrationRequest
		     ↓
		@Valid
		     ↓
		❌ Validation fails
		     ↓
		Controller method doesn't continue

		For @Valid on an @RequestBody, Spring MVC uses:

		MethodArgumentNotValidException

		to represent the validation failure.

	9. Handling the validation errors

		Instead of letting Spring return whatever default error response it has, we can create our own handler.

		Use:

		@RestControllerAdvice
		public class ValidationExceptionHandler {

		    @ExceptionHandler(MethodArgumentNotValidException.class)
		    public ResponseEntity<?> handleValidationErrors(
		            MethodArgumentNotValidException exception) {

		        var errors = exception.getBindingResult()
		                .getFieldErrors();

		        // ...
		    }
		}

		The important idea is:

		@RestControllerAdvice

		basically says:

		"This class can handle exceptions coming from my controllers."

		And:

		@ExceptionHandler(MethodArgumentNotValidException.class)

		says:

		"If this particular validation exception happens, use this method."

	10. Get all the validation errors

		We can get the individual field errors:

		exception.getBindingResult()
		         .getFieldErrors()

		Then turn them into our own response format:

		@RestControllerAdvice
		public class ValidationExceptionHandler {

		    @ExceptionHandler(MethodArgumentNotValidException.class)
		    public ResponseEntity<?> handleValidationErrors(
		            MethodArgumentNotValidException exception) {

		        List<ValidationError> errors =
		                exception.getBindingResult()
		                        .getFieldErrors()
		                        .stream()
		                        .map(error -> new ValidationError(
		                                error.getField(),
		                                error.getDefaultMessage()
		                        ))
		                        .toList();

		        return ResponseEntity
		                .badRequest()
		                .body(errors);
		    }
		}

		And our response object:

		public record ValidationError(
		        String field,
		        String message
		) {}
	11. What does the client receive?

		If the client sends:

		{
		    "username": "ab",
		    "email": "hello",
		    "password": "123"
		}

		Spring finds:

		username → invalid
		email    → invalid
		password → invalid

		Our exception handler collects them.

		The API can then return something like:

		[
		    {
		        "field": "username",
		        "message": "Username must be between 5 and 20 characters"
		    },
		    {
		        "field": "email",
		        "message": "Email address is invalid"
		    },
		    {
		        "field": "password",
		        "message": "Password must be at least 8 characters"
		    }
		]

		with a:

		400 Bad Request

		This is useful because the client gets all the validation problems at once, instead of fixing one error, sending the request again, finding another error, and repeating the process.

	12. The exception doesn't mean something catastrophic happened

		This is worth understanding.

		You might think:

		"The user entered an invalid password. Why are we throwing an exception?"

		From a business perspective, invalid input isn't necessarily some catastrophic event.

		But Spring MVC needs a way to say:

		"This request failed validation, so stop the normal controller flow and deal with the validation errors."

		MethodArgumentNotValidException is the mechanism Spring MVC uses for that.

		So don't think of it as:

		Bad password
		    ↓
		Something terrible happened
		    ↓
		EXCEPTION!!!

		Think of it more like:

		HTTP request
		     ↓
		Create RegistrationRequest
		     ↓
		Run validation
		     ↓
		❌ Validation failed
		     ↓
		Stop controller execution
		     ↓
		MethodArgumentNotValidException
		     ↓
		@RestControllerAdvice
		     ↓
		Build error response
		     ↓
		400 Bad Request

		Entity mapping — the basics

@Entity goes on the class. It tells JPA "this Java class maps to a database table." Without it, JPA ignores the class entirely. By default the table name matches the class name.

@Table(name = "users") overrides the table name. Use it when your class name and table name differ, which they usually do (class User, table users; class OrderItem, table order_items). You can also specify schema, unique constraints, and indexes here.

@Id marks the primary key field. Every entity needs exactly one (or a composite key, which is rarer).

@GeneratedValue(strategy = GenerationType.IDENTITY) tells JPA the database generates the ID. Four strategies exist:

IDENTITY — uses an auto-increment column. Simple, works with MySQL/Postgres. The catch: JPA can't batch inserts because it needs the ID back immediately.
SEQUENCE — uses a database sequence. Preferred with Postgres/Oracle. Allows batching.
AUTO — let the provider decide. Usually fine, but you lose control.
TABLE — a separate table tracks IDs. Portable but slow. Avoid unless you have a reason.

For most projects starting out, IDENTITY is fine. Switch to SEQUENCE when you care about bulk insert performance.

@Column customizes the column mapping. You'll use it for:

name = "email_address" when the field name and column name differ
nullable = false for NOT NULL
unique = true for a unique constraint
length = 500 for varchar length (default is 255)
columnDefinition = "TEXT" when you need a specific SQL type

If you don't need any of that, skip @Column entirely — JPA maps the field by its name.

Relationships

This is where JPA earns its keep and also where people get burned.

@ManyToOne — many of this entity belong to one of that. This is the "child" side of a parent-child relationship. Example: many Order entities belong to one User. On Order you'd write:

java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id")
private User user;

The @JoinColumn names the foreign key column in the orders table. Always set fetch = FetchType.LAZY here — the default is EAGER, which fetches the User every time you load an Order, whether you asked for it or not. This is the single biggest performance mistake with JPA. Just make it a habit to write LAZY every time.

@OneToMany — the other side. On User:

java
@OneToMany(mappedBy = "user")
private List<Order> orders;

mappedBy says "the Order entity owns this relationship via its user field." This is critical: without mappedBy, JPA thinks it's a separate relationship and creates a join table. mappedBy tells it "no, look at the other side, the foreign key already lives there."

Default fetch for @OneToMany is LAZY, which is correct. Don't change it.

@OneToOne — one to one. Same pattern: one side owns it (has @JoinColumn), the other side has mappedBy. Default fetch is EAGER; change it to LAZY.

@ManyToMany — creates a join table. On one side:

java
@ManyToMany
@JoinTable(
    name = "user_roles",
    joinColumns = @JoinColumn(name = "user_id"),
    inverseJoinColumns = @JoinColumn(name = "role_id")
)
private Set<Role> roles;

Honest advice: most @ManyToMany relationships eventually need extra columns on the join table (created date, granted-by-whom, etc.). When that happens, you have to break it into two @OneToManys with an explicit join entity anyway. A lot of experienced engineers just start there and skip @ManyToMany.

cascade on any relationship controls what happens to related entities when you save/delete the parent. Common ones:

CascadeType.PERSIST — save the parent, save the children too
CascadeType.ALL — includes remove, which is dangerous; deleting the parent deletes all children
orphanRemoval = true — remove a child from the parent's collection and it gets deleted from the database

Use CascadeType.ALL only when the child cannot exist without the parent (an OrderItem doesn't exist without its Order). Never on @ManyToOne — you'll delete the parent when you delete one child.

Repository layer

@Repository — you don't need this on interfaces that extend JpaRepository. Spring picks them up regardless. It's only useful on classes where you're implementing a repository yourself, and even then it mostly just translates persistence exceptions.

@Query — write JPQL when method names get ugly:

java
@Query("select u from User u where u.email = :email and u.active = true")
Optional<User> findActiveByEmail(@Param("email") String email);

@Param binds the method parameter to the :email placeholder. Use nativeQuery = true when you need raw SQL.

@Modifying — required on any @Query that isn't a SELECT (UPDATE, DELETE). Without it, Spring tries to execute the query as a SELECT and fails. Also requires a transaction, so pair with @Transactional.

@Transactional — mark service methods that hit the database. Reads can be @Transactional(readOnly = true) — Hibernate skips dirty checking, which is a real speedup for large result sets. Writes get plain @Transactional. Put this on your service methods, not repositories.

The often-forgotten but important ones

@Enumerated(EnumType.STRING) — when a field is an enum. Always use STRING, never ORDINAL (the default). ORDINAL stores the enum's position (0, 1, 2), which silently breaks the moment someone reorders the enum values. STRING stores the name. It's slightly bigger and vastly safer.

@Transient — this field is not persisted. Use it for computed values, caches, anything that lives only in memory.

@Embeddable and @Embedded — when a group of fields belongs together but isn't a separate entity. Example: Address (street, city, postal code) embedded inside User. The fields live in the same table as the parent. Good for keeping value objects grouped without over-normalizing.

@Version — optimistic locking. Add a Long version field with @Version and JPA increments it on every update. If two transactions try to update the same row with the same version, one wins and the other gets an exception. Extremely useful in concurrent systems; effectively free to add.

@Lob — for large objects (long text, byte arrays). Maps to CLOB/BLOB in the database.

@CreatedDate, @LastModifiedDate, @CreatedBy, @LastModifiedBy — auditing. Add @EntityListeners(AuditingEntityListener.class) to the entity, @EnableJpaAuditing on a config class, and these fields get populated automatically. Every entity in a real system needs createdAt and updatedAt, so learn this early.

A realistic entity, end to end
java
@Entity
@Table(name = "orders")
@EntityListeners(AuditingEntityListener.class)
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String orderNumber;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private OrderStatus status;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", nullable = false)
    private User user;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    @CreatedDate
    private Instant createdAt;

    @LastModifiedDate
    private Instant updatedAt;

    @Version
    private Long version;

    // constructors, getters, setters
}

Every choice in there has a reason: LAZY on the @ManyToOne to avoid unwanted joins, mappedBy on the @OneToMany so there's no accidental join table, orphanRemoval because an item can't exist without its order, EnumType.STRING for safe enum storage, @Version for concurrent safety, auditing fields because every real entity needs them.

Want me to go deeper on relationships (they're the part that trips everyone up), or on the auditing/transactional setup?



50. UserDetails interface  is the Spring Securit dedicated interface for the security 
	notion of "who someone is "

	A security system needs to represent an actor. In the general case that actor could be a person, another service, a script — anything making a request. What it needs to hold is at least three pieces of information:

	An identifier — something that names this actor uniquely. A username, an email, an account number.
	A credential — something only this actor should know or possess, used to prove they are who they claim. A password, a private key, a token.
	Their permissions — what this actor is entitled to do. Sometimes called roles, sometimes authorities, sometimes scopes.

		UserDetails
	├── getUsername()       → the identifier
	├── getPassword()       → the credential (hashed)
	├── getAuthorities()    → the permissions
	├── isEnabled()         → account switched on?
	├── isAccountNonLocked()      → account locked out?
	├── isAccountNonExpired()     → account expired?
	└── isCredentialsNonExpired() → password expired?

	The first three methods are the identifier / credential / permissions trio. The last four are lifecycle flags — ways to disable an account without deleting it. Spring Security checks all four during login and rejects the login if any is false.

	UserDetails is an interface. Spring Security ships a default implementation called User (in the package org.springframework.security.core.userdetails

	The workflow

		At login, something produces a UserDetails from your data source (this is the UserDetailsService's job — we'll cover it under Authentication).

		After login, that UserDetails gets wrapped inside an Authentication object (also under Authentication).

		On every subsequent request, that Authentication is loaded from wherever it was stored (session, token) and made available to your code as the current identity.
		Inside your controllers, you can access the current UserDetails by injecting @AuthenticationPrincipal UserDetails user as a method parameter, or by calling SecurityContextHolder.getContext().getAuthentication().getPrincipal().

		The principal is always a UserDetails (or the string "anonymousUser" if no one's logged in). That word "principal" is worth internalizing — in security jargon, the principal is the actor an action is being performed on behalf of. Spring Security uses it everywhere.

	UserDetails is Spring Security's word for "an identity." It has an identifier, a credential, and permissions. It is not your entity, and your entity is not it. They're two different things that happen to describe overlapping data.

51.Authentication - Authentication answers one question: can you prove you are who 
   you claim to be?

   That's the whole idea. Someone shows up claiming to be korah@example.com. Authentication is the process of checking that claim against evidence. If the evidence holds up, they're authenticated. If it doesn't, they're not. There's no gray area — it's a binary outcome.

	The evidence takes different forms depending on the scheme:

	Password — you claim to be Korah, you present the password Korah set. System hashes what you presented and compares to the stored hash.
	Token — you present a token that a trusted authority previously issued. System verifies the token's signature and trusts what it says about you.
	Certificate — you present a client certificate signed by a CA the system trusts.
	Biometric — you present a fingerprint that matches a template on file.

	Different schemes, same shape: claim + evidence → yes or no.

	Phase 1: unauthenticated. You've presented a claim ("I'm Korah") and evidence ("here's my password"), but nothing has been verified yet. It's just a request for authentication.

	Phase 2: authenticated. The evidence checked out. Now the same identity carries proof that it was verified — it's been "authenticated." This is what gets stored and passed around after login.

	Authentication

	This is the interface representing "an authentication request or an authenticated identity" (both phases). Its shape:

	Authentication
	├── getPrincipal()      → who (usually a UserDetails)
	├── getCredentials()    → the evidence (usually the password, cleared after auth)
	├── getAuthorities()    → what they're allowed to do
	├── isAuthenticated()   → phase 1 (false) or phase 2 (true)
	└── getName()           → convenience: the username

	The important mental shift: UserDetails is what your data source returns. Authentication is what the security system passes around. UserDetails is data; Authentication is data plus a verification status.

	Concrete implementation: UsernamePasswordAuthenticationToken. This is the class you'll actually see and use. It has two constructors, and this is the design that carries the two-phase idea:

			// Constructor 1: unauthenticated (phase 1)
		new UsernamePasswordAuthenticationToken(username, password)
		// → isAuthenticated() returns false

		// Constructor 2: authenticated (phase 2)
		new UsernamePasswordAuthenticationToken(principal, credentials, authorities)
		// → isAuthenticated() returns true

		The class enforces this — the phase-1 constructor sets the authenticated flag to false and there is no setter to change it to true. The only way to get an authenticated version is to go through the phase-2 constructor with the authorities argument. This means you can't accidentally create a "trust me, I'm authenticated" object without actually having authorities to hand over. Small detail, meaningful safety property.

	AuthenticationProvider

	If Authentication is the noun, AuthenticationProvider is the verb. It's the interface for "something that can turn an unauthenticated Authentication into an authenticated one." Its shape:

		AuthenticationProvider
	├── authenticate(Authentication) → Authentication (throws if invalid)
	└── supports(Class<?>) → boolean (do I handle this type of auth?)

	The authenticate method takes a phase-1 Authentication and returns a phase-2 one, or throws AuthenticationException if the evidence doesn't hold up.

	Why is this an interface with an implementation, rather than just a method? Because there are many ways to authenticate. Username/password against a database is one way. Verifying a JWT is another. Checking an LDAP directory is another. Each way is a different AuthenticationProvider. The supports() method lets the system pick the right provider for a given Authentication type.

	The one you'll actually use is DaoAuthenticationProvider. "DAO" here means data access object — this provider authenticates against a data source. It handles UsernamePasswordAuthenticationToken and does exactly two things when its authenticate() is called:

	Loads the user from a data source (via UserDetailsService — coming next)
	Compares the presented password against the stored hash (via PasswordEncoder)

	If both work, it builds a phase-2 UsernamePasswordAuthenticationToken with the user's UserDetails as the principal and the authorities from that UserDetails. If either fails, it throws.

	AuthenticationManager

	If there can be many providers, something needs to coordinate them. That's AuthenticationManager. Interface:

	AuthenticationManager
	└── authenticate(Authentication) → Authentication (throws if invalid)

	Same method signature as AuthenticationProvider — deliberately. The AuthenticationManager is the facade over one or more providers. You hand it a phase-1 Authentication, it figures out which provider(s) can handle that type, delegates to them, and returns the result.

	The standard implementation is ProviderManager. It holds a List<AuthenticationProvider> and iterates through them, asking each supports(authType) until one says yes, then delegates to that one's authenticate(). If no provider supports the type, or the supporting provider throws, the manager throws.

	Why this indirection? Because most apps only have one provider, but the abstraction is future-proofing. If you later add "also allow login via API tokens," you write a second provider and register it — the rest of the app that calls authenticationManager.authenticate(...) doesn't change.

	UserDetailsService

	The last piece. When DaoAuthenticationProvider needs to load a user, it doesn't reach into your database itself — it delegates to a UserDetailsService. That interface has one method:

	UserDetailsService
	└── loadUserByUsername(String username) → UserDetails

	That's the entire contract. The provider says "give me the user with this username." Your implementation says how. Query a database, read a file, call a REST API — the provider doesn't care. It just needs a UserDetails back, or a UsernameNotFoundException if there isn't one.

	This is where your code plugs into the framework. Everything else — the Authentication, the provider, the manager — is Spring Security's. UserDetailsService is the seam. It's the class you have to write.

	SecurityContext is a wrapper around a single Authentication. It exists as a container so the framework has one place to look for "the current identity" without needing to pass an Authentication reference through every method. That's it — it's basically a holder object.

	SecurityContextHolder is a thread-local storage for the current request's SecurityContext. When any code, anywhere in your app, calls SecurityContextHolder.getContext().getAuthentication(), it's reading from this thread-local. This is how your controllers can find out who's logged in without you passing the Authentication down through your service layers — it's ambient, keyed to the current thread.

	But there's a problem: thread-locals die when the request ends. The current thread returns to the pool, its thread-local gets cleared, and the next request comes in on a fresh thread with an empty SecurityContextHolder. If we stopped after the first three lines, the login would authenticate the user for the current request only — the very next request they made would see them as anonymous again.

	SecurityContextRepository solves this. It's the abstraction for "store the security context somewhere it can survive between requests." The implementation you want — HttpSessionSecurityContextRepository — stores it in the HTTP session. That's the fourth line: take the context, save it to the session so that when the next request arrives, a filter earlier in the chain (SecurityContextHolderFilter) can pull it back out and load it into the thread-local for that new thread.

	The request and response parameters on saveContext() are there because the repository needs to know which session to write to (from the request) and, depending on the implementation, might need to set a cookie header (on the response) — for example a repository that also writes a Set-Cookie for SameSite handling. Just pass them through.

	Returning something useful. The authenticated.getPrincipal() object is a framework UserDetails, not your entity — it has the username, encoded password, and authorities, but not your id or name. If your frontend wants those to render a profile chip, you have to load the entity.
